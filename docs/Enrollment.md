# BaronDesk Agent : Station Enrollment (First Connection) Architecture

This document describes how a new station gets its identity the first time it contacts the backend: the one-time enrollment token, the station key pair, the signed enrollment request, admin approval and the hand-over to the DPAPI credential store.

## 1. What the Station Sends on First Contact

Before the WSS link exists, the station has no credential. It proves three things in one signed request:

| Field | Security role |
|---|---|
| `oneTimeToken` | Authorises *this* enrollment. Generated by an admin in the dashboard, single use, never logged |
| `mac`, `ip` | Informational, shown to the approving admin. **MAC is not authentication** |
| `serialNumber`, `machineName`, `agentVersion` | Which station is asking (`Machine.serialNumber`) |
| `agentPublicKey` | Base64 DER SubjectPublicKeyInfo of the station's own **ECDSA P-256** key → `Machine.agentPublicKey` |
| `signedAt`, `signature` | Proof of possession of the matching private key, over the token, identity and key |

Signed input (UTF-8, joined with `\n`), ECDSA-SHA256, DER signature:

```text
BARONDESK-ENROLL-V1
<oneTimeToken>
<serialNumber>
<mac>
<ip>
<agentPublicKey>
<signedAt>
```

The **private key never leaves the station**: it is generated locally and kept as PKCS#8 in `station.key` (DPAPI, machine scope, SYSTEM + Administrators only). No shared secret is baked into the installer; every station has its own identity.

## 2. Flow

```text
Admin (dashboard)          Station (elevated prompt)          ServiceCore                         Backend
      │ generate one-time token     │                                │                                  │
      │────────────────────────────►│ --set-enrollment-token          │                                  │
      │                             │──► enrollment.token (DPAPI)     │                                  │
      │                             │                                │ start: no station credential     │
      │                             │                                │ create key pair → station.key    │
      │                             │                                │── TLS (pinned cert) ────────────►│
      │                             │                                │── POST /enrollment/request ─────►│ verify signature,
      │                             │                                │◄─ { status: "PENDING" } ─────────│ record public key
      │◄──────────────────────── approval request ─────────────────────────────────────────────────────│
      │ approve ───────────────────────────────────────────────────────────────────────────────────────►│
      │                             │                                │── same request, new signedAt ───►│ same key? newer?
      │                             │                                │◄─ { status: "ENROLLED",          │
      │                             │                                │     stationToken, machineId } ───│
      │                             │                                │ station.credential (DPAPI)       │
      │                             │                                │ delete enrollment.token          │
      │                             │                                │── WSS upgrade, Bearer <JWT> ────►│
```

| Answer | Agent behaviour |
|---|---|
| `PENDING` | Asks again every `EnrollmentPollSeconds` (default 15 s), same key, logged once |
| `ENROLLED` + valid `stationToken` | Stores the JWT in DPAPI, deletes the one-time token, continues to the WSS connect |
| `ENROLLED` without a usable token | Logged as an error, keeps polling |
| `REJECTED`, HTTP 401 / 403 / 410 | Deletes the spent token, logs CRITICAL, stays unenrolled |
| Network error, 5xx, 400, bad JSON | Retries with the reconnect backoff (`ReconnectBaseDelaySeconds` … `ReconnectMaxDelaySeconds`) |

The station stays **locked** the whole time (fail closed). Enrollment runs only when there is no station credential **and** an enrollment token is provisioned; otherwise the agent connects with its stored credential, or stays locked and offline when it has none (see `CredentialStore.md` §5).

---

## 3. Transport Security

- `HttpEnrollmentClient` uses the **same certificate pin** as the WSS link (`CertificatePinning`). On a mismatch the TLS handshake fails, so the one-time token is never sent.
- No proxy, no redirects: the token can only go to the pinned server.
- Endpoint: `Agent:EnrollmentUrl`, or by default `https://<ServerUrl host:port>/enrollment/request` (`http://` only in Development).
- Responses are capped at 64 KB; the request times out after 15 s.

---

## 4. What the Backend Checks

The backend answers every request with HTTP 200 and a `status`: `PENDING` until an admin approves the machine, then `ENROLLED` with `{ stationToken, machineId }`, or `REJECTED` with a `reason` when retrying cannot help. On each request it checks:

1. **Signature:** the `signature` verifies against `agentPublicKey` over the signed input above (`INVALID_SIGNATURE` otherwise).
2. **Freshness:** `signedAt` is valid and strictly newer than the last accepted request for the same token, so a captured request cannot be replayed (`STALE_SIGNED_AT`).
3. **Token:** the one-time token exists and has not expired (`INVALID_ENROLLMENT_TOKEN`).
4. **Key pinning:** the first accepted request pins the public key to the pending machine. A later request with another key is refused (`PUBLIC_KEY_MISMATCH`), and so is a new enrollment for a serial number another key already holds (`SERIAL_NUMBER_TAKEN`).
5. **Release of the credential:** after approval, the token is spent and the `stationToken` goes only to a request signed by the pinned key. Someone who steals the one-time token alone cannot collect the station credential.
6. **Identity hints:** `mac` and `ip` are shown to the approving admin; they are never trusted as identity.

A station that was rejected or revoked can enroll again with a fresh token for its branch: it goes back to `PENDING` with its new key and waits for approval.

The mock server checks the signature and pins the key in the same way, so the agent can be tested end to end without the backend.

## 5. Provisioning Commands (elevated prompt)

```powershell
# one-time token from the dashboard (piped or typed hidden, never as an argument)
"<one-time token>" | BaronDeskAgent.ServiceCore.exe --set-enrollment-token
BaronDeskAgent.ServiceCore.exe --clear-enrollment-token

# re-enroll a station (e.g. after revocation): forget the identity first
BaronDeskAgent.ServiceCore.exe --clear-station-token     # removes station.credential AND station.key
```

`--set-station-token` remains as a manual fallback (a JWT issued out of band).

Development only: `Agent:EnrollmentToken` may hold the one-time token in configuration (rejected at startup elsewhere, like `Agent:StationToken`).

## 6. Files

| File (`%ProgramData%\BaronDeskAgent\Data`) | Content | Lifetime |
|---|---|---|
| `enrollment.token` | One-time token (DPAPI) | Until `ENROLLED` / `REJECTED` |
| `station.key` | ECDSA P-256 private key, PKCS#8 (DPAPI) | Until `--clear-station-token`; regenerated if unreadable (a cloned disk image gets a new identity) |
| `station.credential` | Station JWT (DPAPI) | Until rotated / cleared |

All three use `ProtectedFile`: DPAPI `LocalMachine` with per-purpose entropy, protected DACL (SYSTEM + Administrators), atomic write with the final ACL, plaintext buffers zeroed.

| `An_enrolled_station_never_contacts_the_enrollment_endpoint` | No enrollment once a credential exists |

## Implementation Summary

- Station key pair (ECDSA P-256) generated on the station, stored with DPAPI
- Signed `POST /enrollment/request` over the pinned TLS link
- `PENDING` polling, `ENROLLED` → DPAPI credential, `REJECTED` → token spent
- One-time token provisioning (`--set-enrollment-token`), Development config fallback
- Same request and answer contract as the backend (`PENDING` / `ENROLLED` / `REJECTED`)
- Mock server endpoint with signature verification and key pinning

After enrollment the station authenticates with its station JWT (see `CredentialStore.md`); the key pair is what proves, during enrollment, that the credential goes to the machine that asked for it.
